# Typed request shapes in `--help-full` — design

Date: 2026-08-13
Status: draft, awaiting review

## Goal

Replace the bare field-name list that write commands print under `Request fields`
with a typed JSON sample, generated from the Kiota models at build time and
emitted as `RequestExamples.g.cs`, the way `ResponseExamples.g.cs` is generated
from the response DTOs.

An agent writing a body today sees `publishers` and `year` as undifferentiated
names. It cannot see that `publishers` is a list of `{name, url}` or that `year`
is a number, and learns both by being refused once.

Doing this before books is the point: every write command added afterwards gets
its shape for free instead of being retrofitted.

Out of scope: required-ness (see [Known gap](#known-gap-required-ness)), value
validation, any new command, any change to which endpoints are called.

## Grounding

Read from `src/GrimoireCli/Generated/Models` as generated by
`tools/generate-api-client.sh` against the pinned stack. Property-shape counts
below were taken by scanning that tree; they are the state of the API surface at
Grimoire v1.5.6, not invariants.

### The types are in the models

The roadmap entry assumed the types were reachable only from the spec, because
the generated properties are composed-type wrappers and unwrapping them needs
reflection that Native AOT trims. The first half does not hold. The wrapper
carries the scalar as a plain property:

```csharp
public partial class GameSystemUpdate_is_explicit : IComposedTypeWrapper, IParsable
{
    public bool? Boolean { get; set; }
    public global::GrimoireCli.Generated.Models.GameSystemUpdate_is_explicitMember1? GameSystemUpdateIsExplicitMember1 { get; set; }
}
```

`…Member1` is the `null` branch of FastAPI's `anyOf: [bool, null]` — an empty
model with no fields. `Boolean` is the type.

Trimming only applies to the shipped AOT binary. A build-time generator that
references `GrimoireCli` reflects freely, which is what `GenerateResponseExamples`
already does over the response DTOs.

Every composed wrapper in the tree — 175 of them — has exactly this shape: one
`…Member1` shell plus one scalar. 123 `string`, 37 `bool`, 15 `int`. There is no
wrapper whose value branch is a `$ref`, and none with more than two branches, so
"unwrap to the single non-`Member1` property" is a total rule rather than a
heuristic with a fallback.

## Decision: the models are the source, not the spec

Both carry what is needed — the spec has the types, the models have the wire
names — and the risk is that they disagree. Three reasons the models win:

**Correctness.** `JsonBodyInput.Validate` rejects a body against
`GetFieldDeserializers().Keys`. If help were generated from the spec and the
model lost a field, help would advertise fields the CLI itself refuses. Kiota
[#2338](https://github.com/microsoft/kiota/issues/2338) is exactly that failure
mode, and `tools/normalize-spec.py` exists because it already bit this repo.
Generating from the models makes the disagreement unrepresentable.

**Drift detection.** `ResponseExamplesDriftTest` keeps the checked-in output
honest by running the generator in-process and diffing. A spec-sourced generator
could not: `tools/generate-api-coverage.py` fetches from
`http://host.docker.internal:9481/api/openapi.json` and needs a running stack,
which CI has not got. Reflection over the models runs anywhere.

**The models are already downstream of the spec.** They are generated from it and
committed so a version bump produces a reviewable diff. Reading them is reading
the spec, one deterministic step later, through the same normalisation the
runtime client uses.

## Design

### The generator

`tools/GenerateRequestExamples` — a console project referencing `GrimoireCli`,
structured like `GenerateResponseExamples`. Emits
`src/GrimoireCli/Commands/RequestExamples.g.cs`: a `Dictionary<Type, string>` of
pretty-printed JSON samples, with `For(Type)` and `All`, line endings normalised
so the checked-in output is stable cross-platform.

Two tools rather than one. The inputs have nothing in common —
`SampleJsonWalker` reads STJ DTOs via `[JsonPropertyName]`, this one reads Kiota
models via `GetFieldDeserializers()` and unwraps composed types — so a shared
walker would be an abstraction with two implementations that share only their
indentation logic. Each tool keeps a name that describes what it does, and each
drift test fails for one reason.

### Discovery

Every public `IParsable` in the `GrimoireCli.Generated.Models` namespace that is
not nested, not a `…Member1` shell, and not `HTTPValidationError` or
`ValidationError` — per `CLAUDE.md`, the spec's only two response-only schemas.
84 models today.

Generating all of them, rather than the three commands use, is what makes a new
write command free. The alternative — an allowlist in the generator, as
`generate-api-coverage.py` keeps `IMPLEMENTED` — puts a generator edit in the
path of every new command, which is the friction this item exists to remove. The
cost is string literals for models no command reaches; `ResponseExamples.g.cs` is
8 KB for 8 DTOs, and 84 mostly-small request bodies land far below anything that
matters against an AOT binary.

### Walking a model

Wire names come from `GetFieldDeserializers().Keys` — the set `Validate`
enforces — sorted ordinally, each resolved to its property by case-insensitive
match with underscores stripped (`character_builder_url` → `CharacterBuilderUrl`).

**A key that resolves to no property fails the generator.** Not a skip, not a
warning. An unresolvable key means the help text and the validator have diverged,
which is the one outcome this design exists to prevent, and it must stop the
build rather than quietly emit a shape missing a field.

Each resolved property renders by type:

| Property type | Renders as |
|---|---|
| `string` | `"<string>"` |
| `int` | `0` |
| `bool` | `false` |
| `List<string>` | `["<string>"]` |
| `List<int?>` | `[0]` |
| `IComposedTypeWrapper` | unwrap to the single non-`…Member1` property, then as above |
| enum | `"<member1|member2|...>"` |
| model reference | nested object, recursed |
| `List<model>` | one-element array of the recursed object |
| `UntypedNode` | `{}` |
| model with no fields beyond `AdditionalData` | `{}` |

Recursion carries a depth guard of 5. Nothing in the tree is self-referential
today; the guard is there so a future model that is fails visibly instead of
hanging the build.

Placeholders only — no realistic-value overrides. `GenerateResponseExamples`
substitutes `"Shadowrun 6 DE"` and `227` because a response sample illustrates
what comes back. In a body template the same values read as a suggestion of what
to send.

### Rendering

Pretty-printed, two-space indent, matching the response samples so the two
sections under `--help-full` read as one pair:

```
Request shape:
  {
    "character_builder_url": "<string>",
    "cover_book_id": "<string>",
    "description": "<string>",
    "dice_materials": [
      "<string>"
    ],
    "publishers": [
      {
        "name": "<string>",
        "url": "<string>"
      }
    ],
    "year": 0
  }
```

### Call sites

`AddRequestShape<T>()` replaces
`AddRequestShape<T>(T model, params string[] preamble)`, mirroring
`AddResponseExample<T>()`: the sample is looked up by type, not walked from an
instance. Section title becomes `Request shape`, symmetric with `Response shape`.
`Wrap()` and the comma-list rendering are deleted with their only caller.

The `preamble` parameter goes with them. All three of its uses exist to say in
prose what the sample now shows structurally, and a preamble that survives would
invite the next command to re-describe its own shape above it.

Three call sites in `SystemsCommand`:

- `update` — `GameSystemUpdate`. Preamble drops to nothing: "the body is a flat
  object of these, all optional" is what the sample already shows, and "`id` is
  not one of them" is a claim about an absent field, which the comment rules
  forbid stating.
- `batch-tag` — `BulkAddTags`. Preamble "The body is a flat object of:" goes; the
  sample is the object. "ids and tags are both required" stays in Notes.
- `batch-update` — switches from `GameSystemBulkItem` to `GameSystemBulkUpdate`,
  the envelope, which is also the model `Validate` already parses against. Today
  help lists the *item's* fields while the validator accepts only `items` at the
  root, and a hand-written sentence is the sole thing stopping a reader from
  pasting those names as root keys. The nested sample states the wrapper
  structurally. "Each item requires `id`" stays in Notes.

After this, the model in the help is the model in `Validate` for every command,
with no exception to remember.

## Known gap: required-ness

Kiota emits every property nullable, so the models cannot express that `ids` and
`tags` are mandatory or that each bulk item needs an `id`. Those statements stay
hand-written in Notes, where they are today.

The spec has `required` and the models do not, which is the one thing that would
argue for reading the spec. It does not outweigh the three reasons above: a
required-ness annotation is a sentence that changes about once per API version,
while a name/type list changes every version and is what an agent reads on every
invocation. Hand-maintaining the rare thing to generate the frequent thing is the
right side of that trade.

## Testing

- `RequestExamplesDriftTest` — runs `tools/GenerateRequestExamples` into a temp
  path and diffs against the checked-in file, as `ResponseExamplesDriftTest` does.
  This is what makes "regenerate the client" and "regenerate the shapes" a single
  reviewable step rather than a thing to remember.
- `RequestExamplesJsonValidTest` — parses every sample in `All`, as the response
  counterpart does.
- A generator-level assertion that every `GetFieldDeserializers()` key across all
  84 models resolves to a property. The generator already fails on this; the test
  states it as a property of the whole surface, so a Grimoire version bump that
  introduces an unmappable name is a red test with a name that explains itself.
- Existing help-output tests updated for the `Request shape` title and the sample
  body.
- Smoke test unchanged — no endpoint, flag or command changes.

## Risks

**A Kiota version bump changes the composed-wrapper shape.** The unwrap rule
depends on `…Member1` naming and on there being exactly one value branch. If a
future Kiota emits something else, the drift test fails loudly on regeneration
and the rule is revisited — which is the correct outcome, and better than the
spec-sourced alternative, where the same change would silently desynchronise help
from validation.

**Binary growth from unused samples.** 84 samples of string literals, none
trimmable since they sit in a static initialiser. Measured against the AOT
binary after implementation; if it is ever material, an allowlist is a small
change to one file.
