# Grimoire 1.6.0 — compatibility assessment

Date: 2026-08-14
Status: research, no decisions taken
Branch: `epic/grimoire-1.6.0`

Measured against the `hunterreadca/grimoire:edge` image pushed 2026-08-14, which
carries `a12b3c0 Enhancement: Add openapi response model to all endpoints (#347)`.
Upstream 1.6.0 is unreleased; `edge` is the only place this behaviour exists, so
every number here is provisional until a tag ships.

The 1.5.6 pin in `temp/grimoire/` is untouched — ongoing 1.5.6 work depends on
it. Reference material for this branch goes in `temp/grimoire-main/`.

## The spec now types its responses

| | 1.5.6 | edge |
|---|---|---|
| Component schemas | 86 | **281** |
| Operations | 207 | 233 |
| Success responses | 192 typed as `{}` | **195 of 233 typed** |

The 38 that are still untyped are not a gap: 16 are `204 No Content`, and the
other 22 are binary or redirect endpoints — book files, thumbnails, page images,
system covers, map/token/audio files, campaign banners, and the two OIDC
redirects. **Every JSON success response in the API now carries a schema.**

This removes the documented reason response DTOs are hand-written
(`CLAUDE.md`, "API client generation": *no success response carries a schema …
those are hand-written from `temp/grimoire/`'s serializers and stay
hand-written*). That sentence becomes false at 1.6.0 and the rule it justifies
goes with it.

missing or extra fields:

That is the useful result: reading the server's serializers by hand produced the
same shapes the server now publishes, so the switch is a mechanical replacement
rather than a re-modelling exercise, and no command's output changes.

## What the switch actually costs

Nothing here is speculative except where marked:

1. **Generation is already parameterised.** `tools/generate-api-client.sh` takes
   `GRIMOIRE_SERVER`, so generating from the edge container is one command. Kiota
   is installed and pinned by `kiota-lock.json`.
2. **~34 call sites move**, plus 5 services: every `AppJsonContext.Default.<Dto>`
   argument and each `ConsoleOutput.WriteJson` type parameter.
3. **`AppJsonContext` loses its response registrations** and the 31 files under
   `src/GrimoireCli/Models/` are deleted — except `AppConfig`, which is local
   config and not a response.
4. **The response-example generator needs rework.** `tools/GenerateResponseExamples`
   reflects over `AppJsonContext`'s `[JsonSerializable]` attributes; generated
   Kiota models are not registered there and are not STJ-attributed at all, so
   the walker's input changes. This is the largest single unknown and the one
   worth prototyping first — `--help-full`'s response shapes are a shipped
   feature.
5. **Generated type names are ugly where FastAPI namespaces collide** —
   `backend__routers__addons___schemas__StatusResponse` is a real name in the
   spec, and we already live with `Backend__routers__systems___schemas__MetadataSearch`
   on the request side. Aliases at the call sites, or accept them.
6. **Recheck kiota#2338.** `tools/normalize-spec.py` exists because Kiota drops
   properties behind `anyOf: [array of $ref, null]`. That wrapper is how FastAPI
   emits `Optional[list[Model]]`, which the new response schemas will be full of,
   so the workaround likely matters more than before, not less. Unverified: no
   generation has been run against this spec yet.
7. **Tests** — `tests/GrimoireCli.Tests/Models/` (31 DTO tests across 5 files)
   either move to the generated types or are deleted as testing generated code.
   The response-example drift tests move with item 4.

Estimate, assuming item 4 has a clean answer: one to two sessions of mechanical
work with a large diff and no behaviour change. If item 4 has no clean answer,
the DTOs may be worth keeping *for help generation only*, which would make the
whole switch not worth doing.

## The auth change is the real 1.6.0 story

`da55c9d Security: Add refresh tokens and revocable sessions (#346)` is not
mentioned in the request that prompted this note and matters more than the
schemas.

New endpoints: `POST /api/auth/refresh`, `POST /api/auth/logout`,
`GET /api/auth/sessions`, `DELETE /api/auth/sessions/others`,
`DELETE /api/auth/sessions/{session_id}`.

**The access token's lifetime drops from 30 days to 30 minutes.**
`backend/sessions.py` on main: `ACCESS_TOKEN_EXPIRE_MINUTES` defaults to 30
(minutes), with `REFRESH_TOKEN_EXPIRE_DAYS` defaulting to 30 (days) and carried
in a `grimoire_refresh` **cookie**. 1.5.6 issues one 30-day bearer token and
nothing else (`temp/grimoire/backend/auth.py:54-57`, `TOKEN_EXPIRE_DAYS`).

Consequences for this CLI, which stores a bearer token in
`~/.grimoire-cli/config.json` and treats a 401 as terminal:

- Against a stock 1.6.0 server, a saved token stops working **30 minutes** after
  login. Every command after that fails with "log in again" until the user does.
  This is a hard break in the CLI's core workflow, not a degradation.
- Staying logged in requires storing and rotating the refresh **cookie** —
  `POST /api/auth/refresh` declares no bearer security and takes the
  `grimoire_refresh` cookie as its input, returning the same `{token, user}`
  shape as login and re-setting both cookies. Rotation includes reuse detection,
  so a stale cookie is not merely useless but a signal to the server.
- `docs/authentication.md`'s sharpest recorded divergence from abs-cli — "**No
  refresh endpoint.** … a 401 is terminal" — ends at 1.6.0. abs-cli already has
  transparent refresh, so the design is there to harvest rather than invent.
- `GET /api/about` now declares `HTTPBearer`. Our daily version check calls it
  with a token, so this is probably fine, but the pre-login path needs checking.

**One CLI version targets one server version.** There is no dual-version
support and none is wanted: CLI `0.1.x` supports Grimoire 1.5.6, and whoever
stays on 1.5.6 stays on `0.1.x`. When 1.6.0 releases, this branch moves
`MinSupportedVersion` and `MaxTestedVersion` to 1.6.0 together and the
compatibility matrix gains a row — the CLI never has to detect which server it
is talking to, and refresh is implemented unconditionally as a feature rather
than behind a version gate.

That is what makes this an epic rather than a PR: not the branching of
behaviour, but the waiting. The work cannot merge until upstream tags 1.6.0, and
`main` keeps taking new 1.5.6-era commands in the meantime.

## Not affected

- **`SECRET_KEY` fail-closed (#345).** `docker/docker-compose.yml` already sets
  `SECRET_KEY=dev-only-not-a-real-secret`, which is not the shipped default, so
  the dev stack should still boot. Verify by booting our compose against `edge`.
- **Login's response shape.** Still `{token, user}` (`LoginResponse`), so token
  extraction and storage keep working as-is.
- **Request bodies.** Already generated from the spec; nothing in this note
  changes them.

## Suggested order

1. Prototype item 4 — generate from edge into a throwaway path and find out
   whether `--help-full` response shapes can be produced from Kiota models. It
   gates whether the DTO switch is worth doing at all.
2. Implement refresh: persist the `grimoire_refresh` cookie, rotate on 401,
   surface `auth sessions` / revocation if wanted. Unconditional — no version
   gate.
3. Do the mechanical DTO switch.
4. Move `MinSupportedVersion` **and** `MaxTestedVersion` to 1.6.0 and add a
   matrix row, only once a 1.6.0 tag exists upstream. Never against `edge`:
   `CLAUDE.md` pins the reference to a released version precisely because `main`
   carries work no instance runs.

## Living alongside `main`

The branch waits for an upstream tag of unknown date while `main` keeps shipping
1.5.6-era commands, so drift is the standing cost:

- **Merge `main` into the epic regularly**, not once at the end. Every new
  command on `main` arrives with hand-written DTOs and `AppJsonContext`
  registrations — exactly what step 3 deletes — so a late merge means resolving
  the same conflict many times over.
- **A command added on `main` after step 3 lands needs doing twice**: once the
  1.5.6 way for `main`, once the generated way on the epic. Cheaper to accept
  than to freeze `main`, but worth knowing before starting step 3 rather than
  after.
- **CI on this branch cannot pin a released server.** `docker/docker-compose.yml`
  pins `1.5.6`; the epic must point at `edge` or `nightly`, which move under it.
  A red smoke test on the epic may mean upstream changed, not that the branch
  broke — so treat epic CI as a signal, not a gate, until a 1.6.0 tag exists to
  pin.

## Reproducing the measurements

```bash
docker run -d --name grimoire-edge -p 9482:9481 \
  -e SECRET_KEY=edge-eval-only-not-a-real-secret \
  -v grimoire-edge-data:/data -v grimoire-edge-lib:/library \
  hunterreadca/grimoire:edge
# The published port is not reachable from the devcontainer under
# docker-outside-of-docker; use the container's bridge address instead:
EDGE=$(docker inspect grimoire-edge --format '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}')
curl -s "http://${EDGE}:9481/api/openapi.json" -o /tmp/spec-edge.json
```
