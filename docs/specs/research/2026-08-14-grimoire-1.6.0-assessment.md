# Grimoire 1.6.0 — compatibility assessment

Date: 2026-08-14
Status: research, no decisions taken
Branch: `epic/grimoire-1.6.0`

Measured against the `hunterreadca/grimoire:edge` image pushed 2026-08-14, which
carries `a12b3c0 Enhancement: Add openapi response model to all endpoints (#347)`.
Upstream 1.6.0 is unreleased; `edge` is the only place this behaviour exists, so
every number here is provisional until a tag ships.

The 1.5.6 pin in `temp/grimoire/` is untouched — ongoing 1.5.6 work depends on
it. Reference material for this branch goes in `temp/grimoire-main/`.

## The spec now types its responses

| | 1.5.6 | edge |
|---|---|---|
| Component schemas | 86 | **281** |
| Operations | 207 | 233 |
| Success responses | 192 typed as `{}` | **195 of 233 typed** |

The 38 that are still untyped are not a gap: 16 are `204 No Content`, and the
other 22 are binary or redirect endpoints — book files, thumbnails, page images,
system covers, map/token/audio files, campaign banners, and the two OIDC
redirects. **Every JSON success response in the API now carries a schema.**

This removes the documented reason response DTOs are hand-written
(`CLAUDE.md`, "API client generation": *no success response carries a schema …
those are hand-written from `temp/grimoire/`'s serializers and stay
hand-written*). That sentence becomes false at 1.6.0 and the rule it justifies
goes with it.

## Our hand-written DTOs already match, field for field

All 31 DTOs in `src/GrimoireCli/Models/` were matched against the 281 schemas by
field-set overlap. **31 of 31 match exactly** — same JSON property names, no
missing or extra fields:

| Ours | Spec schema |
|---|---|

| `GameSystemDetail` (33, via inheritance) | `SystemDetail` |
| `GameSystemRef` | `BookSystemRef` |
| `Book` / `BookDetail` / `BookSummary` / `BookListResponse` | `BookOut` / `BookDetail` / `BookListItem` / `BookListResponse` |
| `MeResponse` | `AuthMeResponse` |
| `ScanStatus` / `ScanTriggerResult` | `ScanStatusResponse` / `…addons___schemas__StatusResponse` |
| `AddonInstalled` / `AddonAvailable` / `AddonListResponse` / `AddonSettings` / `AddonUpgrade` / `AddonUpgradeFailure` / `RefreshResult` / `UpgradeAllResult` | `InstalledAddon` / `AvailableAddon` / `AddonListResponse` / `AddonSettingsResponse` / `AddonUpdated` / `AddonUpdateFailure` / `RefreshIndexResponse` / `UpdateAllResponse` |
| `MetadataSource` / `MetadataSourceList` / `MetadataCandidate` / `MetadataSearchResult` / `MetadataFieldDiff` / `MetadataFetchResult` | `MetadataSource` / `MetadataSourcesResponse` / `MetadataCandidate` / `MetadataSearchResponse` / `MetadataDiffField` / `MetadataFetchResponse` |

That is the useful result: reading the server's serializers by hand produced the
same shapes the server now publishes, so the switch is a mechanical replacement
rather than a re-modelling exercise, and no command's output changes.

## What the switch actually costs

Nothing here is speculative except where marked:

1. **Generation is already parameterised.** `tools/generate-api-client.sh` takes
   `GRIMOIRE_SERVER`, so generating from the edge container is one command. Kiota
   is installed and pinned by `kiota-lock.json`.
2. **~34 call sites move**, plus 5 services: every `AppJsonContext.Default.<Dto>`
   argument and each `ConsoleOutput.WriteJson` type parameter.
3. **`AppJsonContext` loses its response registrations** and the 31 files under
   `src/GrimoireCli/Models/` are deleted — except `AppConfig`, which is local
   config and not a response.
4. **The response-example generator converges with the request one, rather than
   needing invention.** `tools/GenerateRequestExamples`'s `KiotaSampleWalker`
   already walks Kiota models: it discovers them by reflecting
   `GrimoireCli.Generated.Models` for non-nested public `IParsable` classes,
   takes wire names from `GetFieldDeserializers().Keys`, and maps each onto its
   PascalCase property with `Resolve()`, throwing when a deserialised field has
   no property. That is the whole mechanism the response side needs.

   **Decided:** `tools/GenerateRequestExamples` is renamed to something like
   `GenerateJsonExamples` and generates samples for *every* model, with
   `tools/GenerateResponseExamples` and its `SampleJsonWalker` deleted outright.
   One tool, one walker, one sample registry.

   That drops the request/response distinction rather than reimplementing it,
   which is the right shape: the split only exists because the two sides had
   different sources. Consequences to carry out with it —

   - **Discovery loses its exclusions.** Today it skips `HTTPValidationError` /
     `ValidationError` as "the spec's only response-only schemas", which stops
     being true when the spec has ~200 of them. "Every model in
     `GrimoireCli.Generated.Models`" becomes the whole rule.
   - **The two help-section helpers survive, the two lookups do not.**
     `AddRequestShape<T>()` and `AddResponseExample<T>()` render different
     section titles and both stay, but they read one dictionary instead of
     `RequestExamples.For` and `ResponseExamples.For`.
   - **Four test files consolidate**: `RequestExamplesTests`,
     `RequestExamplesDriftTest`, `ResponseExamplesDriftTest` and
     `ResponseExamplesJsonValidTest` become one drift test and one validity test
     over the single generated file.
   - **`SampleJsonWalker`'s `JsonElement` case goes with it.** That case exists
     for the metadata diff's polymorphic fields; its replacement is the
     `UntypedNode` case in item 6.

5. **The output path is the real unknown, not the help path.**
   `ConsoleOutput.WriteJson(result, AppJsonContext.Default.X)` uses STJ
   source-generation. Kiota models carry no STJ attributes and are not
   registered on any `JsonSerializerContext`, so printing one means
   `KiotaJsonSerializer` (or reading the raw body and passing it through
   untouched). Two consequences worth deciding deliberately:

   - **Today's stdout is a projection, not the server's bytes.** Our DTOs drop
     any field the server sends that we do not model. Kiota models are
     `IAdditionalDataHolder`, so unknown fields survive a round trip — strictly
     better fidelity for a CLI whose contract is "JSON in, JSON out", and an
     argument for the switch independent of the schemas.
   - **Field order and formatting change hands.** Whatever writes the JSON
     decides both, and `ResponseExamplesJsonValidTest` plus every smoke-test
     `jq` assertion reads that output.

6. **The two untyped diff fields need checking against real generator output.**
   `MetadataDiffField.current` is `anyOf: [{}, {type: null}]` and `incoming`
   carries no type at all, which is the spec being honest — their JSON type is
   decided per row by `field`. Kiota most likely emits `UntypedNode` for both;
   the walker then needs an `UntypedNode` case emitting `"<any>"`, the same
   answer the STJ walker already gives for `JsonElement`. Unverified until a
   generation is run.
5. **Generated type names are ugly where FastAPI namespaces collide** —
   `backend__routers__addons___schemas__StatusResponse` is a real name in the
   spec, and we already live with `Backend__routers__systems___schemas__MetadataSearch`
   on the request side. Aliases at the call sites, or accept them.
6. **Recheck kiota#2338.** `tools/normalize-spec.py` exists because Kiota drops
   properties behind `anyOf: [array of $ref, null]`. That wrapper is how FastAPI
   emits `Optional[list[Model]]`, which the new response schemas will be full of,
   so the workaround likely matters more than before, not less. Unverified: no
   generation has been run against this spec yet.
7. **Tests** — `tests/GrimoireCli.Tests/Models/` (31 DTO tests across 5 files)
   either move to the generated types or are deleted as testing generated code.
   The response-example drift tests move with item 4.

Estimate, assuming item 4 has a clean answer: one to two sessions of mechanical
work with a large diff and no behaviour change. If item 4 has no clean answer,
the DTOs may be worth keeping *for help generation only*, which would make the
whole switch not worth doing.

## The auth change is the real 1.6.0 story

`da55c9d Security: Add refresh tokens and revocable sessions (#346)` is not
mentioned in the request that prompted this note and matters more than the
schemas.

New endpoints: `POST /api/auth/refresh`, `POST /api/auth/logout`,
`GET /api/auth/sessions`, `DELETE /api/auth/sessions/others`,
`DELETE /api/auth/sessions/{session_id}`.

**The access token's lifetime drops from 30 days to 30 minutes.**
`backend/sessions.py` on main: `ACCESS_TOKEN_EXPIRE_MINUTES` defaults to 30
(minutes), with `REFRESH_TOKEN_EXPIRE_DAYS` defaulting to 30 (days) and carried
in a `grimoire_refresh` **cookie**. 1.5.6 issues one 30-day bearer token and
nothing else (`temp/grimoire/backend/auth.py:54-57`, `TOKEN_EXPIRE_DAYS`).

Consequences for this CLI, which stores a bearer token in
`~/.grimoire-cli/config.json` and treats a 401 as terminal:

- Against a stock 1.6.0 server, a saved token stops working **30 minutes** after
  login. Every command after that fails with "log in again" until the user does.
  This is a hard break in the CLI's core workflow, not a degradation.
- Staying logged in requires storing and rotating the refresh **cookie** —
  `POST /api/auth/refresh` declares no bearer security and takes the
  `grimoire_refresh` cookie as its input, returning the same `{token, user}`
  shape as login and re-setting both cookies. Rotation includes reuse detection,
  so a stale cookie is not merely useless but a signal to the server.
- `docs/authentication.md`'s sharpest recorded divergence from abs-cli — "**No
  refresh endpoint.** … a 401 is terminal" — ends at 1.6.0. abs-cli already has
  transparent refresh, so the design is there to harvest rather than invent.
- `GET /api/about` now declares `HTTPBearer`. Our daily version check calls it
  with a token, so this is probably fine, but the pre-login path needs checking.

**One CLI version targets one server version.** There is no dual-version
support and none is wanted: CLI `0.1.x` supports Grimoire 1.5.6, and whoever
stays on 1.5.6 stays on `0.1.x`. When 1.6.0 releases, this branch moves
`MinSupportedVersion` and `MaxTestedVersion` to 1.6.0 together and the
compatibility matrix gains a row — the CLI never has to detect which server it
is talking to, and refresh is implemented unconditionally as a feature rather
than behind a version gate.

That is what makes this an epic rather than a PR: not the branching of
behaviour, but the waiting. The work cannot merge until upstream tags 1.6.0, and
`main` keeps taking new 1.5.6-era commands in the meantime.

## Not affected

- **`SECRET_KEY` fail-closed (#345).** `docker/docker-compose.yml` already sets
  `SECRET_KEY=dev-only-not-a-real-secret`, which is not the shipped default, so
  the dev stack should still boot. Verify by booting our compose against `edge`.
- **Login's response shape.** Still `{token, user}` (`LoginResponse`), so token
  extraction and storage keep working as-is.
- **Request bodies.** Already generated from the spec; nothing in this note
  changes them.

## Trial results (2026-08-14, run against `edge`)

Generated with the pinned Kiota 1.34.1 from the normalised edge spec into
`temp/kiota-trial/` — 937 files, 741 models; the normaliser collapsed 40
`anyOf`-nullable arrays. A scratch console app parsed a real metadata-fetch
payload, re-serialised it, and ran the checked-in `KiotaSampleWalker` over four
response models. Everything below is measured, not predicted.

### Answered: the untyped diff fields

`current` and `incoming` generate as **`UntypedNode?`**, and parsing resolves
each row to a concrete subclass — `UntypedString`, `UntypedInteger`,
`UntypedArray`, `UntypedObject`, with an absent value staying `null`. So the
polymorphism survives the switch intact.

The walker renders both as `{}` today, because `UntypedNode` is an `IParsable`
with no field deserializers. It needs an `UntypedNode` case emitting `"<any>"` —
the same answer `SampleJsonWalker` gives for `JsonElement`, four lines.

### Answered: AOT, and the output path

- **The round trip works**: `JsonParseNodeFactory` → the model's own
  `CreateFromDiscriminatorValue` → `KiotaJsonSerializer.SerializeAsStringAsync`.
- **AOT is not a problem.** The trial published with `PublishAot=true` with no
  trim or AOT warnings and produced byte-identical output to the JIT run. This
  was the risk that could have sunk the whole plan; it is answered.
- **Standalone serialisation needs the writer factory registered**
  (`SerializationWriterFactoryRegistry.DefaultInstance.ContentTypeAssociatedFactories`).
  The generated client does this in its constructor, so in the CLI it is already
  done — but a generator or test that serialises outside the client must do it.

Three output-contract changes, each needing a deliberate decision:

| | today (STJ DTOs) | Kiota models |
|---|---|---|
| Undeclared server fields | **dropped** | **kept** (`AdditionalData`), at every level |
| Explicit `null` | written | **omitted** |
| Formatting / order | indented, declaration order | compact, alphabetical |

The first is a straight win for a "JSON in, JSON out" tool. The second and third
are visible changes to stdout: `"current": null` disappears from a metadata diff,
and every smoke-test `jq` assertion reads reordered, unindented output. Note
`.current` in `jq` yields `null` for an absent key too, so most consumers cannot
tell — but that is an argument, not a decision.

There is a third option the trial makes obvious: **do not re-serialise at all.**
Parse into the generated model for the fields the CLI actually reads
(`BulkExit.CodeFor`, `ScanExit.CodeFor`), and print the server's bytes verbatim.
That is maximal fidelity and sidesteps formatting entirely.

### Answered: the existing walker handles response models

`KiotaSampleWalker.Render` ran unmodified over four shapes — flat
(`AddonSettingsResponse`), `UntypedNode`-bearing (`MetadataDiffField`), nested
(`MetadataFetchResponse`) and deep (`SystemDetail`, 2602 characters of sample).
No crashes, no missing-property throws. The single tool plan holds.

### New blocker: upstream types some arrays as `list[Any]`

**18 array properties across 4 schemas declare `items: {}`** — array of
anything — against 154 that are typed, out of 172 array-valued properties.
No `anyOf`-wrapped array hides the same problem; that count is zero. All four
schemas are ones our busiest commands read:

Counted on the **raw** spec from the server. The normalised copy the generator
consumes reports 21 across 7, because collapsing `anyOf: [array, null]` wrappers
exposes three more plain arrays — a trap worth remembering when quoting numbers
at upstream, who only sees the raw one.

| Schema | Untyped arrays |
|---|---|
| `BookOut` (`systems/_schemas.py`), `BookDetail` (`books/_schemas.py`) | `authors`, `artists`, `genres`, `urls` |
| `SystemSummary`, and `SystemDetail` by inheritance | `publishers`, `character_builder_urls`, `urls`, `genres`, `dice_materials` |

Kiota therefore generates `UntypedNode?` for each, where our hand-written DTOs
declare `List<string>?` and `List<LinkEntry>?`. Two costs: the generated models
are **weaker** than what they would replace, and the help shape degrades from
`["<string>"]` to `"<any>"` for the fields agents most often read.

The cause is upstream and looks like an oversight rather than a decision —
`backend/routers/books/_schemas.py` declares `authors: list[Any]`,
`artists: list[Any]`, `genres: list[Any]`, `urls: list[Any]` at lines 146-151,
while `tags: list[str]` on line 160 is correct and the *request* model twenty
lines above already has `Optional[list[str]]` and `Optional[list[LinkEntry]]`.
The systems schemas repeat the pattern.

**This is worth raising upstream before the switch**, with those line numbers:
`list[str]` and `list[LinkEntry]` would make the generated models strictly better
than the hand-written ones. If it stays `list[Any]`, the options are to keep
hand-written DTOs for those four schemas, or accept losing the element types.

One thing to check either way: if the underlying JSON columns really can hold
heterogeneous values, `list[Any]` is *correct* and our `List<string>?` DTOs have
been lying — in which case a book with an object in `authors` would fail to
deserialise today. Worth a probe against the fixture library.

## Living alongside `main`

The branch waits for an upstream tag of unknown date while `main` keeps shipping
1.5.6-era commands, so drift is the standing cost:

- **Merge `main` into the epic regularly**, not once at the end. Every new
  command on `main` arrives with hand-written DTOs and `AppJsonContext`
  registrations — exactly what step 3 deletes — so a late merge means resolving
  the same conflict many times over.
- **A command added on `main` after step 3 lands needs doing twice**: once the
  1.5.6 way for `main`, once the generated way on the epic. Cheaper to accept
  than to freeze `main`, but worth knowing before starting step 3 rather than
  after.
- **CI on this branch cannot pin a released server.** `docker/docker-compose.yml`
  pins `1.5.6`; the epic must point at `edge` or `nightly`, which move under it.
  A red smoke test on the epic may mean upstream changed, not that the branch
  broke — so treat epic CI as a signal, not a gate, until a 1.6.0 tag exists to
  pin.

## Reproducing the measurements

```bash
docker run -d --name grimoire-edge -p 9482:9481 \
  -e SECRET_KEY=edge-eval-only-not-a-real-secret \
  -v grimoire-edge-data:/data -v grimoire-edge-lib:/library \
  hunterreadca/grimoire:edge
# The published port is not reachable from the devcontainer under
# docker-outside-of-docker; use the container's bridge address instead:
EDGE=$(docker inspect grimoire-edge --format '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}')
curl -s "http://${EDGE}:9481/api/openapi.json" -o /tmp/spec-edge.json
```
