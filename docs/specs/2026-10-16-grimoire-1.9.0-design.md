# Target Grimoire 1.9.0

This bumps the targeted server from Grimoire 1.8.0 to 1.9.0 ahead of
grimoire-cli v0.7.0. It updates the commands that already exist, and nothing
else. The new 1.9.0 areas get tracking issues and are scoped later.

## What 1.9.0 changes for the CLI

All of the following comes from the specs of the running 1.8.0 and 1.9.0
stacks.

- **Surface:** 360 operations become 399. No operation was removed, and no
  wrapped operation changed its path, method or parameters.
- **New routes (39):**
  - share links: 8, plus 4 public `/share/{token}` routes
  - Codex DB: 8
  - book and map export, cut-out shapes, page size, OTFBM: 10
  - character importers: 4
  - audio chapters
  - `duplicates describe`
  - the OIDC button icon: 2
- **New fields in request bodies the CLI validates:**
  - `codex_id` on `BookUpdate`, `BookBulkItem`, `GameSystemUpdate` and
    `GameSystemBulkItem`, used by `books update` / `books batch-update` /
    `systems update` / `systems batch-update`
  - `parent_kind` and `parent_label` on `LinkRequest`, used by
    `duplicates link`
- **New fields in responses**, passed through untouched:
  - `codex_id`
  - `variant_main_*`, `variant_kind` and `variant_label`
  - `track_number` and `disc_number`
  - `share_links_*`
  - `oidc_button_*`
  - `unreadable_name`

## Supported range: 1.9.0 – 1.9.0

Regenerating makes the five commands above accept the new body fields. A 1.8.0
server would drop them through Pydantic `extra='ignore'` and still answer 200.
That is the "flag an in-range server would ignore" case
(`docs/grimoire-compatibility.md`), so the floor rises to 1.9.0. Anyone on
1.8.0 stays on grimoire-cli v0.6.0.

The commit is a `feat:`, not a breaking change. Supporting a new server is a
minor bump (`docs/releasing.md#versioning`), the CLI's own surface is
unchanged, and #89 raised the floor to 1.8.0 the same way. The reason goes in
the commit body and the matrix.

## Work

1. **Re-pin.**
   - Set `docker/docker-compose.yml` to `hunterreadca/grimoire:1.9.0`.
   - Check out `temp/grimoire` at `v1.9.0`. Verify it against the image's
     `/app/backend` with `diff -rq`; only `backend/tests` may differ.
2. **Regenerate.**
   - Run `bash tools/generate-api-client.sh`, then the `--help-full` samples
     (`tools/GenerateJsonExamples`).
   - Regenerate `docs/grimoire-api-coverage.md`. The total goes from 238/360
     to 238/399.
3. **Range.**
   - In `GrimoireApiClient.cs`, set `MinSupportedVersion` and
     `MaxTestedVersion` to `1.9.0`.
   - In the matrix, set `0.6.0 | 1.8.0 | superseded by 0.7.0` and
     `0.7.0 | 1.9.0 | current, on main`.
   - Update the "`main` targets" sentence and the README compatibility line.
   - Update any tests that pin the version strings.
4. **Audit behaviour.**
   - Diff `backend/routers/`, `backend/models/` and `backend/services/` from
     `v1.8.0` to `v1.9.0`.
   - Check the diff against what the CLI documents: help Notes,
     `docs/grimoire-api-notes.md`, and the exit-code readers
     (`ReadStringProperty`, `HasItems`).
   - Fix help and notes wherever a documented rule changed.
   - Leave command behaviour unchanged. If the audit finds a change that needs
     a command to behave differently, stop and raise it.
   - The release notes name some candidates: the scan skipping non-UTF-8
     filenames, variant main labels, audio ordering, and Magazines & Zines as
     a built-in book category.
5. **Verify.**
   - Run format, build and the unit tests.
   - Run `bash docker/seed.sh` and `bash docker/smoke-test.sh` against the
     1.9.0 stack.
